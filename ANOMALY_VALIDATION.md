# One-year anomaly model audit

Frozen window: `2025-07-26T00:00:00Z` through
`2026-07-26T00:00:00Z`.

The benchmark reads 105,120 completed five-minute buckets for each of Base,
Optimism, and Arbitrum One. The first 8,640 buckets (30 days) are warm-up.
The remaining 96,480 buckets per chain are scored in arrival order.

## Reproduce

```bash
npm install
# Set PINAX_JWT in .env.
npm run anomaly:benchmark
npm run check
```

The job uses finalized The Graph Substreams data and timestamp-to-block lookup.
It checkpoints every 50,000 blocks under ignored
`output/anomaly-benchmark/` files and resumes after interruption. Annual mode
fails on a missing block, incomplete chunk, invalid cache boundary, or absent
Substreams endpoint. It never switches to year-scale JSON-RPC ingestion.

The frozen ranges contain 15,767,526 Base blocks, 15,768,000 Optimism blocks,
and 126,148,051 Arbitrum One blocks (3,155 source chunks before boundary
overlap). This is intentionally an offline, quota-heavy job. A measured Base
checkpoint completed 50,000 consecutive blocks and resumed at the first
partial-bucket block; no annual result is published from that partial run.

After all coverage gates pass, the only generated result intended for commit is
`benchmark/anomaly-annual-v2.json`. Its `artifactChecksum` is SHA-256 over the
canonical artifact payload, excluding that checksum field. The API returns
`404` before that file exists and rejects a mismatched checksum; no fixture is
presented as annual evidence. Raw bucket caches are never committed.

## Evaluation contract

The evaluation is prequential: score bucket *t* using only accepted buckets
strictly before *t*, decide whether to quarantine it, then update the model.
It does not shuffle data, fit on the future, or retroactively expand a detected
point across a full incident window.

Event recall and latency use official mainnet incident windows. A detection
must begin inside the event window, with one five-minute boundary tolerance.
One alert episode counts once regardless of how many anomalous buckets it
contains. Precision-recall is preferred to ROC because official incidents are
rare. The NAB-inspired continuous latency score is `exp(-latencyMinutes / 30)`;
the artifact also retains exact median minutes. Unmatched alerts are reported
as **unmatched episodes**, not confirmed
false positives: public status histories are not complete ground truth.

The methodology follows the streaming and latency emphasis of the
[Numenta Anomaly Benchmark](https://arxiv.org/abs/1510.03336), avoids the
point-adjusted F1 inflation documented in
[rigorous time-series anomaly evaluation research](https://arxiv.org/abs/2109.05257),
and uses precision-recall for rare events following
[Saito and Rehmsmeier](https://journals.plos.org/plosone/article?id=10.1371/journal.pone.0118432).

## Frozen labels and exclusions

The versioned manifest is `benchmark/anomaly-labels-v1.json`. Every entry
records chain, UTC window, affected component, observability, source URL, and
an explicit exclusion reason where applicable.

Accuracy labels include only official mainnet sequencing, block-production, or
transaction-inclusion incidents whose effect can appear in canonical block,
transaction, receipt, gas, fee, sender, or timestamp metrics:

- [Base status history](https://status.base.org/history)
- [Optimism status history](https://status.optimism.io/history/1)
- [Arbitrum status history](https://status.arbitrum.io/default/history/1)

RPC-only failures, bridge incidents, explorer failures, Flashblocks-only
incidents, testnets, and planned maintenance are excluded. Historical OP-stack
stalls reconstructed from official wall-clock outage windows are marked
`observer-simulation`. Recovered canonical blocks can retain regular block
timestamps and therefore do not independently prove what a user observed
during the stall.

## Compared models

1. `bayesian-nig-v1`: the original rolling Bayesian detector.
2. `seasonal-mad`: a 30-day weekday/weekend five-minute rolling median/MAD
   reference.
3. `bayesian-nig-conformal-v2`: the corrected model proposed by this audit.

V2 uses:

- independent state for every chain and metric;
- `log1p` for positive metrics and clamped logit for ratios;
- a robust chain-wide transformed median/MAD empirical-Bayes prior;
- the exact Normal–Inverse-Gamma posterior update;
- a Student-t posterior predictive distribution;
- local weekday/weekend UTC five-minute slots with chain-wide fallback;
- accepted prequential residuals for conformal tail calibration;
- Benjamini–Yekutieli correction across available metrics in each bucket;
- high-only alerts for failed-transaction rate and block interval;
- quarantine of abnormal observations from the rolling baseline.

The 32 frozen candidates span slot minimum `{7,14}`, calibration window
`{14,30}` days, warning FDR `{0.005,0.01}`, critical FDR
`{0.0005,0.001}`, and warning persistence `{2,3}`.

Tuning uses `2025-08-25` through `2026-03-25`, clean-window alert burden, and a
fixed seeded suite of TPS spikes/drops, failure surges, congestion, 5–60 minute
stalls, and regime changes. The provider-outage fixture has missing source
metrics and is excluded from chain-anomaly truth. Parameters freeze before the
`2026-03-26` through `2026-07-26` holdout.

Selection and promotion are separated to prevent holdout leakage:

1. synthetic critical recall at least 95%;
2. fewest unmatched tuning episodes;
3. lowest median tuning detection latency;
4. stable parameter key as a deterministic tie-break;
5. freeze that one candidate, then require its holdout observable-event recall
   to be no worse than v1.

V2 is promoted only when those gates pass. Otherwise the artifact records the
failed comparison and retains v1.

## Dashboard and API

`GET /api/anomaly/benchmark` returns the compact artifact or a clear `404`
when it has not been generated. `GET /api/anomaly/research` always returns the
versioned source and model index, so methodology remains reviewable while the
annual job is incomplete. The Anomalies dashboard renders:

- three aligned annual chain timelines with official incident bands;
- warning/critical detection markers;
- selectable observed-versus-expected event details with 99% and 99.9% bands;
- event-level v1/MAD/v2 precision-recall comparison;
- nominal-versus-empirical calibration;
- exact per-chain coverage, event, alert, and latency results.
- an indexed research-to-implementation map for NAB latency scoring, evaluation
  without point adjustment, and precision-recall-first rare-event reporting.

All charts are native SVG. No chart package or client-side model is involved.

## Live liveness guard

Each configured chain may provide `secondaryRpcUrl`. A critical liveness stall
requires both providers to return agreeing finalized heads and timestamps.
Head disagreement, a failed secondary provider, or a stale primary without
quorum is source degradation, never a chain anomaly. Canonical metric ingestion
continues from the primary provider while the degraded source is visible in the
heartbeat API and dashboard.

## Safety boundary

Benchmarking is read-only. Anomaly execution can store metric buckets, cursors,
alerts, wallet warnings, and webhook attempts only. Neither path can create or
mutate an incident, claim, decision, settlement, or payout.

This audit optimizes precision-first chain-health warnings. Address-level wallet
behavior remains outside the benchmark; a wallet watch subscribes to chain
alerts and is not represented as wallet-specific anomaly detection.

A collective dispute still requires:

1. one wallet-signed confirmed transaction report;
2. a matching published deterministic rule;
3. The Graph-derived affected wallets and violations.
